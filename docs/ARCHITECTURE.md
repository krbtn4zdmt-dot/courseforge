# Architecture

## High-level flow

```
User chat ──▶ Intake (parse topic + timeframe + prefs)
                 │
                 ▼
          Planner ──▶ topic type, subtopics, time budget
                 │
                 ▼
          Researcher ──▶ search web/YouTube/Wikipedia, score + store sources
                 │
                 ▼
     Curriculum Designer ──▶ syllabus (days → lessons, objectives, minutes)
                 │           [user previews/edits here]
                 ▼
   ┌──── per lesson, just-in-time (Inngest job) ────┐
   │  Lesson Writer ──▶ Examiner ──▶ Fact-Checker   │
   │        ▲                            │          │
   │        └──── rewrite if flagged ────┘          │
   └────────────────────────────────────────────────┘
                 │
                 ▼
            Stored in Postgres ──▶ rendered in UI
```

## Time-budget engine (`src/lib/pipeline/timeBudget.ts`)
Pure function, fully unit-tested. It decides how many minutes each day gets and how they're split; the Curriculum Designer fills in the content.

**Input:** `days` (1–60), `minutesPerDay` (15–90; intake snaps answers to 15 / 30 / 45 / 60 / 90), `topicType`.
**Output:** per day, `{ dayNumber, reviewMinutes, lessons: { estMinutes, readingMinutes, mediaMinutes, practiceMinutes }[] }`.

Rules, applied per day (all rounding is half-up, i.e. `Math.round`, unless it says `ceil`):
1. **Review block.** Days 1–2: none. Day 3 onward: `reviewMinutes = round(minutesPerDay × 0.10)` of spaced recall on earlier days. Final day: `reviewMinutes = ceil(minutesPerDay × 0.30)` for review and the final quiz (this replaces the 10%, it doesn't add to it). A 1-day course follows the final-day rule.
2. **Teaching time.** `teachingMinutes = minutesPerDay − reviewMinutes`.
3. **Lesson count.** `lessonsPerDay = clamp(ceil(teachingMinutes / 25), 1, 4)`. Split `teachingMinutes` evenly in whole minutes, giving leftover minutes to the earliest lessons. For every input in range, each lesson lands between 10 and 25 minutes; assert this.
4. **Inside a lesson.** `estMinutes` is the whole lesson: reading, videos, practice and quiz. Split it by topic type:

| Topic type | Reading | Media | Practice + quiz |
|---|---|---|---|
| knowledge, hybrid | 55% | 20% | 25% |
| skill | 45% | 15% | 40% |

Round each part to whole minutes and give any rounding difference to reading, so the parts always sum to `estMinutes`.

Every day's lessons plus its review block add up to exactly `minutesPerDay`. The review block is a syllabus item of kind `review`; the 10–25 minute rule applies only to items of kind `lesson`.

Worked examples (5-day course; use these as test cases):

| minutesPerDay | Days 1–2 | Days 3–4 | Day 5 (final) |
|---|---|---|---|
| 15 | 1 lesson: 15 | 1 lesson: 13, review 2 | 1 lesson: 10, review 5 |
| 30 | 2 lessons: 15, 15 | 2 lessons: 14, 13, review 3 | 1 lesson: 21, review 9 |
| 90 | 4 lessons: 23, 23, 22, 22 | 4 lessons: 21, 20, 20, 20, review 9 | 3 lessons: 21, 21, 21, review 27 |

## Generation strategy
- **Syllabus first, fast:** planner + light research + curriculum design, target < 20s. Light research is one Tavily `basic` query per subtopic (the planner's first query), run in parallel, no raw content, no YouTube. If the target is missed in Phase 1, measure where the time goes before changing anything; merging planner and curriculum into one call is the fallback.
- **Deep research after confirm:** one Inngest step runs the remaining queries (Tavily `advanced` with raw content, YouTube, Wikipedia) for the whole course, then Day 1 lessons start. Target for confirm → Day 1 readable stays < 90s.
- **Later days ahead of time:** when a user completes day N, queue generation for day N+2. Also a nightly job that generates the next day for active courses.
- **Unlocking:** Day 1 opens on confirm. Day N opens when every lesson in day N−1 is marked complete. Since finishing day N−1 queues day N+1, the next day is normally ready before it's needed; if it isn't, show its lessons as "being prepared".
- Each lesson is generated by its own Inngest step, so one failure doesn't break the course and retries are automatic.

## Research details
- 2–3 search queries per subtopic, generated by the planner. Light research uses the first; deep research uses the rest.
- **Tavily** (deep research): `search_depth: advanced`, `max_results: 5`, include raw content for top results. Trim raw content to the passages relevant to the subtopic (max ~1,500 words per source) and store it as `grounding` for the Lesson Writer and Fact-Checker. It is never displayed.
- **YouTube** (quota-bound):
  - `search.list` once per subtopic with importance 1 or 2, capped at **8 searches per course**; `type=video`, `relevanceLanguage` = user language, `maxResults=10`.
  - One `videos.list` call (up to 50 ids, `contentDetails,statistics`) for exact durations and view counts; keep 3–25 min videos only. The search API's own duration filter only has <4 / 4–20 / >20 min buckets.
  - One `channels.list` call (up to 50 ids, `statistics`) for subscriber counts.
  - **Score** by log-scaled views, log-scaled channel subscribers, recency, and title relevance. There is no like ratio: the API doesn't return dislikes.
  - **Quota:** the default is 10,000 units/day. `search.list` costs 100 units; the other two cost 1 each. That's ~800 units per course, or about 12 courses/day. Cache search results by normalized query for 7 days. When quota runs out, lessons ship without videos (0 is allowed) and the shortfall is logged. Apply for a quota increase before the beta (task 4.5).
- **Wikipedia:** summary endpoint for key entities in knowledge topics. Send a descriptive `User-Agent` with contact info, as Wikimedia's API policy requires.
- **Source score** (0–1): domain credibility (allowlist boost for `.edu`, `.gov`, official docs, major encyclopedias/publications; penalty for content farms), relevance (one batched `MODEL_FAST` call rating each source 0–1 against its subtopic), recency (for fast-moving topics only). Keep top 3–6 per lesson.
- **Deduplicate** by canonical URL, then by near-duplicate text: Jaccard similarity > 0.8 on 5-word shingles of the grounding text.
- No embeddings in the MVP (see decisions log).

## Data model (Postgres)

```sql
create table profiles (
  id uuid primary key references auth.users on delete cascade,
  display_name text,
  created_at timestamptz default now()
);

create table courses (
  id uuid primary key default gen_random_uuid(),
  user_id uuid references profiles(id) on delete cascade,
  topic text not null,
  topic_type text check (topic_type in ('knowledge','skill','hybrid')),
  days int not null check (days between 1 and 60),
  minutes_per_day int not null,
  level text not null,
  goal text not null,
  status text not null default 'draft'
    check (status in ('draft','syllabus_ready','active','completed','failed')),
  plan jsonb,                -- planner output
  created_at timestamptz default now()
);

create table lessons (
  id uuid primary key default gen_random_uuid(),
  course_id uuid references courses(id) on delete cascade,
  day_number int not null,
  position int not null,
  kind text not null default 'lesson'
    check (kind in ('lesson','review')),
  title text not null,
  objectives text[] not null,
  est_minutes int not null,
  status text not null default 'pending'
    check (status in ('pending','generating','ready','failed')),
  content_md text,
  key_terms jsonb,
  practice_task jsonb,
  video_ids text[],
  fact_check jsonb,
  generated_at timestamptz,
  unique (course_id, day_number, position)
);

create table sources (
  id uuid primary key default gen_random_uuid(),
  course_id uuid references courses(id) on delete cascade,
  url text not null,
  title text,
  source_type text check (source_type in ('web','video','wiki','docs')),
  score real,
  excerpt text,              -- 1–2 sentence summary, safe to display
  grounding text,            -- trimmed source passages (~1,500 words max); pipeline only, never displayed
  unique (course_id, url)
);

create table lesson_sources (
  lesson_id uuid references lessons(id) on delete cascade,
  source_id uuid references sources(id) on delete cascade,
  primary key (lesson_id, source_id)
);

create table questions (
  id uuid primary key default gen_random_uuid(),
  lesson_id uuid references lessons(id) on delete cascade,
  prompt text not null,
  options jsonb not null,     -- [{id, text}]
  correct_option_id text not null,
  explanation text not null
);

create table progress (
  user_id uuid references profiles(id) on delete cascade,
  lesson_id uuid references lessons(id) on delete cascade,
  completed_at timestamptz,
  quiz_score real,
  feedback text check (feedback in ('too_easy','just_right','too_hard')),
  primary key (user_id, lesson_id)
);

create table llm_calls (
  id bigserial primary key,
  course_id uuid references courses(id) on delete set null,
  agent text not null,
  model text not null,
  input_tokens int,
  output_tokens int,
  cost_usd numeric(10,5),
  created_at timestamptz default now()
);
```

Enable Row Level Security on all user tables: users can only read/write rows tied to their own `user_id` (via `courses.user_id` for child tables). Pipeline jobs use the service role key server-side.

**Embeddings note:** Anthropic doesn't offer an embeddings endpoint. The MVP skips embeddings: relevance is a `MODEL_FAST` call and near-duplicates are caught with text shingles (see Research details). If relevance scoring proves weak in the Phase 1 review, add Voyage AI (`voyage-3`, 1024 dims) with `create extension vector` and an `embedding vector(1024)` column on `sources`, and log the change below.

**Quiz answers:** `questions.correct_option_id` is readable by the course owner under RLS, so the answer can be found in the browser. That's accepted for the MVP: quizzes are self-study with nothing at stake, and it keeps feedback instant. Move answer checking to a server route if quizzes ever gate anything.

## Model usage
- `MODEL_SMART` (e.g. `claude-sonnet-5`): planner, curriculum designer, lesson writer
- `MODEL_FAST` (e.g. `claude-haiku-4-5-20251001`): intake parsing, examiner, fact-checker, relevance scoring
- Verify current model names in Anthropic's docs before setting env vars.
